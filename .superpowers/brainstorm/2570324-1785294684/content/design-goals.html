e-cat 设计目标与架构原理

第一部分：设计目标

设计目标

1. Kratos 对齐 保持 Kratos 的微服务理念 —— API-first、可插拔、统一抽象。让熟悉 Kratos 的开发者可以无缝上手
2. Rust 惯用 不强行复制 Go 模式。使用 tower::Service、trait 泛型、零成本抽象。尊重 Rust 生态现有标准，不做「Go in Rust」
3. 类型安全 利用 Rust 类型系统，在编译期捕获错误。Protobuf 定义的错误码、请求/响应类型全部强类型化
4. 可插拔 Registry、Config、Logging、Encoding 全部通过 trait 抽象。默认提供生产可用实现，允许替换
5. 工具链完备 CLI 工具支持项目脚手架、proto 代码生成、运行开发服务。对标 kratos new / proto / run
6. 性能优先 利用 Rust 的零成本抽象，在提供 Kratos 级开发体验的同时，实现 Go 无法企及的吞吐和延迟
7. 可观测 tracing + OpenTelemetry + Prometheus 开箱即用。每个请求都有 trace_id，每个中间件都埋点

核心原则

Kratos 概念 → Rust 实现映射
Kratos (Go) e-cat (Rust) 设计理由
kratos.New() ecat::App::builder() Builder 模式更 Rust 化
http.Handler tower::Service 复用 Rust 生态标准
http.Server axum::Router 社区最主流的 HTTP 框架
grpc.Server tonic::transport::Server 最成熟的 gRPC 实现
proto generate prost + tonic-build Rust 社区标准 protobuf
registry.Discovery Registry trait 可插拔注册发现
config.Source ConfigSource trait 多源配置加载

整体架构分层

e-cat 架构层次
┌──────────────────────────────────────────────────┐
│                  ecat-cli                        │  ← CLI 工具链
│        (new | proto | run | build)               │
├──────────────────────────────────────────────────┤
│              ecat (App 生命周期)                   │  ← 应用编排层
│    AppBuilder → App { http_srv, grpc_srv, ... }  │
├──────────────┬──────────────┬────────────────────┤
│  transport   │  middleware  │     registry       │  ← 核心组件层
│  ─────────   │  ─────────   │     ────────       │
│  HTTP/gRPC   │  recovery    │     etcd/consul    │
│  ecoding     │  tracing     │     dns/memory     │
│              │  auth/...    │                    │
├──────────────┼──────────────┼────────────────────┤
│   config     │   errors     │     metadata       │  ← 基础设施层
├──────────────┴──────────────┴────────────────────┤
│              ecat-protos                         │  ← IDL 定义
│    (共享 protobuf 定义: errors, metadata, ...)    │
└──────────────────────────────────────────────────┘
