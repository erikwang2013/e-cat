Transport 层设计：HTTP/gRPC 统一中间件

这是 e-cat 最核心的架构决策 — 如何让两套协议共享同一套中间件链

方案 A：Trait 抽象 + 协议适配器

统一 Service 接口 + 协议适配器（对标 Kratos）
// 核心 trait —— 所有传输协议的统一接口
#[async_trait]
pub trait Service: Send + Sync {
    async fn call(&self, ctx: Context, input: Request) -> Result;
}

// 中间件就是 Service 的包装器
#[async_trait]
pub trait Middleware: Send + Sync {
    async fn call(&self, ctx: Context, input: Request, next: BoxService) -> Result;
}

// HTTP Server → 将 http::Request 转为 e-cat Request，调用 Service
// gRPC Server → 将 tonic::Request 转为 e-cat Request，调用 Service
//
// 请求流：
//  HTTP Request  ──→ [解码] ──→ ecat::Request ──→ [MW1 → MW2 → Handler]
//  gRPC Request ──→ [解码] ──→ ecat::Request ──→ [MW1 → MW2 → Handler]

优点

  • 完美对应 Kratos 设计
  • 中间件对 HTTP/gRPC 完全透明

缺点

  • 多了抽象层开销
  • 需要维护与 axum/tonic 的适配器

方案 B：直接使用 Axum/Tonic 原生机制 + 共享组件

无统一抽象，共享底层组件
// 不提供统一 Service trait，而是：
// 1. 共享的 Context（metadata、trace_id 等）
// 2. 共享的类型（ecat::Request、ecat::Response、ecat::Error）
// 3. 各自用原生中间件机制：

// HTTP:  axum::middleware::from_fn()
// gRPC:  tonic::service::layer()

// 用户写两次 middleware，但共享逻辑提取到工具函数

优点

  • 零抽象开销，直接使用框架能力
  • 维护成本低

缺点

  • 违背 Kratos 统一抽象理念
  • HTTP/gRPC 各自写中间件

方案 C：Tower-based Service（推荐）

复用 Tower Service Trait + 自定义 Layer
// Rust 生态已有的标准抽象 —— tower::Service
// axum 和 tonic 都基于 tower 构建！

use tower::{Service, Layer};
use std::future::Future;

// e-cat Request = tonic::Request 或 http::Request
// Layer trait = 中间件工厂，生成 Service 包装

// HTTP Middleware
let http_layer = tower::ServiceBuilder::new()
    .layer(RecoveryLayer::new())
    .layer(TracingLayer::new())
    .layer(AuthLayer::new());

// gRPC Middleware —— 完全相同的 layer 链！
let grpc_layer = tower::ServiceBuilder::new()
    .layer(RecoveryLayer::new())
    .layer(TracingLayer::new())
    .layer(AuthLayer::new());

// e-cat 的角色：提供标准 Layer 实现，不重新发明 trait

优点

  • 复用 Rust 生态标准 trait
  • axum/tonic 原生兼容，零适配器
  • 保持中间件共享能力

缺点

  • 与 Kratos 的设计不完全一致
